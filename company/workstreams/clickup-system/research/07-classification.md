# Classification field — value set design (Phase 3 research)

Prepared 2026-09-16. Scope: design an 8–14-value, workspace-wide multi-select "Classification" field describing the **nature/effort type** of work — not department (the space already is the department) and not task type (the kind of item). Also proposes the full custom task-type set for Capture lists and the Founding Punch List, and flags conflicts. Read-only research; no ClickUp writes made.

---

## 1. What "Classification" is for, and what it isn't

Per DECISIONS.md: "Classification = multi-select labels. Research decides the value set (full coverage of effort types)." It replaces the unused **Project** dropdown (Financials/White Paper/Pitch Deck/Research) and is also the field driving the Investors & Fundraising and Real Estate/Buildout carved-out views in the Punch List — so it must double as a **routing/filter axis**, not just a descriptive tag.

Two other fields already cover adjacent ground and must stay out of Classification's lane:
- **Space (department)** — Operations, People, Real Estate, Investors, Meetings, Founding Punch List, etc. Classification must never re-encode "which department."
- **Task type** — the kind of item (Meeting, Document/Deliverable, Structure, Workflow, Idea…). Classification must never re-encode "what shape of artifact this is."
- Also distinct from the proposed **Cross-Department** field (DECISIONS.md 2026-09-16 post-audit), which is about which *other* spaces a task touches, not the nature of the effort.

So Classification's job is the **why/how of the work** — is this one-time or ongoing, offensive or defensive, high-uncertainty or well-understood, governance vs. build. This is the axis PM frameworks call "effort type," "work mode," or "run vs. change."

## 2. Frameworks surveyed

- **Run/Change/Build (a.k.a. RTB vs. CTB) and KTLO vs. growth** (CONFIRMED — mainstream IT/PM vocabulary). Splits work into keep-the-business-running maintenance vs. work that changes/grows the business. Common org split guidance is 60/40–80/20 run:change. Sources: [Rezolve.ai — KTLO](https://www.rezolve.ai/blog/what-it-means-to-be-keeping-the-lights-on-ktlo), [Uplevel — KTLO](https://uplevelteam.com/blog/ktlo-in-software-development), [Meisterplan — Run the Business](https://meisterplan.com/blog/project-portfolio-management/define-project-run-the-business/).
- **Cynefin (Simple/Complicated/Complex/Chaotic/Disorder)** (CONFIRMED as a framework, UNCERTAIN fit for a small pre-opening team). Useful conceptually (how much uncertainty/novelty a task carries) but its 5-domain vocabulary is too academic for two founders labeling tasks fast; we borrow the *idea* (novel/exploratory vs. routine) rather than the domain names. Source: [Wikipedia — Cynefin framework](https://en.wikipedia.org/wiki/Cynefin_framework), [Whatfix — Cynefin](https://whatfix.com/blog/cynefin-framework/).
- **GTD contexts** (CONFIRMED as a framework) — these are about *where/how* an action gets done (@calls, @errands), not the nature of the effort; not directly reusable, but reinforces that a labels field should be short, low-cardinality, and glanceable.
- **Eisenhower urgent/important** (CONFIRMED as a framework) — urgency/importance is a *prioritization* axis, already partly covered by ClickUp's native Priority field and the Punch List's Inbox→Later→Soon→Next→Doing→Waiting status queue (per DECISIONS.md). Classification should not re-implement priority.
- **ClickUp's own guidance draws exactly this run/change-style line for task types** ("Project management: separate tasks, milestones, deliverables, change requests… Bugs, features, improvements, spikes") — confirming the community pattern of a "why kind of work" field distinct from task type. Source: [ClickUp Blog — Task Categories](https://clickup.com/blog/task-categories/), [ZenPilot — Custom Task Types](https://www.zenpilot.com/blog/how-to-best-use-clickups-custom-task-types).
- **Restaurant pre-opening practice** (CONFIRMED, general industry sources, UNCERTAIN Sŏn-specific detail since no founder interview was run for this brief): the field separates capital/one-time build spend (lease, buildout, FF&E) from recurring operating setup (staffing, training, compliance) and from external relationship work (investors, permitting agencies) — mirrors run/change/build plus a "relationship/external" bucket. Sources: [Tilit — 2026 Restaurant Opening Checklist](https://www.tilitnyc.com/blogs/restaurant-business-operations/restaurant-opening-checklist), [Restaurant365 — Opening Checklist](https://www.restaurant365.com/blog/comprehensive-restaurant-opening-checklist-guide/).
- **ClickUp community / feedback board**: labels and multi-select are the same underlying field type in ClickUp ("Labels are exactly the same thing as multi-select… unique to that specific custom field, unlike tags which are across the entire space") — CONFIRMED, source: [ClickUp feedback — Multiple Selections in Custom Fields](https://feedback.clickup.com/feature-requests/p/multiple-selections-in-custom-fields). This confirms Classification-as-Labels is the right field type per DECISIONS.md, and that it will NOT collide with the existing single `investor` Tag (tags are workspace-wide free text; this is a governed value list). No Reddit thread specifically about a "Classification/effort-type" field was found — general community sentiment (ClickUp Help, ZenPilot) converges on "use Task Types for the *kind* of item, use a custom field/label for cross-cutting attributes like this one," which matches the plan already set in DECISIONS.md.
- **ClickUp AI auto-classification** (CONFIRMED existence, UNCERTAIN reliability/cost for this use): 2026 ClickUp AI can auto-classify tasks into task types from content. Since AI is on rollover credits and turned on per use case (STATE.md), do not turn on auto-classification for Classification labels at launch — populate manually/deliberately, revisit later if backlog volume justifies the credit spend. Source: search summary citing ClickUp AI workspace-taxonomy features (2026), [ClickUp Updates 2026](https://clickup.com/learn/topic/project-management/tools/clickup/news/).

## 3. Recommended value set — 12 values

Multi-select (a task can carry more than one — e.g., a task can be both `Founder Decision` and `Investor-Facing`). Designed for full coverage of the ~491-task Founding Punch List content plus the department Capture lists, without duplicating space or task type.

| # | Value | Definition | Sŏn examples | Overlap / exclusivity note |
|---|---|---|---|---|
| 1 | **Build / One-Time Setup** | Work that stands something up once: buildout, systems, vendor onboarding, a process getting created for the first time. Ends when the thing exists. | Lease buildout tasks, HVAC/grease-trap checks, standing up the POS, the SaaS Map rebuild itself | Mutually exclusive with *Recurring/Operating* for the same task — a task is either creating the thing or running it, not both. Overlaps freely with *Capital Spend* and *Vendor/Procurement*. |
| 2 | **Recurring / Operating** | Ongoing, repeats on a cadence once live — the KTLO/run-the-business half of run-vs-change. Not itself a meeting (that's the task type), but the operating cadence a meeting or process belongs to. | Weekly Founders Sync occurrences, standups, recurring budget reviews, shift scheduling once staffed | Excludes *Build/One-Time Setup*. Commonly paired with the `Meeting` task type but not identical to it — a non-meeting recurring checklist (e.g., weekly compliance check) also gets this label. |
| 3 | **Governance / Structure** | Defining how the org itself is organized and decided — roles, policies, the operating agreement, the Scaling People backlog's Structure/Instrument/Process items. Encodes org design, not a specific deliverable's content. | The ~330-task Scaling People backlog, Operating Agreement clauses, S1–S17 book-chapter items, Teams setup | This is the field value that carries the Scaling People backlog going forward (DECISIONS.md: carve-outs must be field-driven, and Scaling People must never appear in carved-out views — so Governance/Structure must explicitly stay OUT of the Investors and Real Estate carved-out view filters). Overlaps with *Founder Decision*. |
| 4 | **Founder Decision** | A choice only a founder can make — irreversible-ish, judgment call, no clear "right" process answer. Distinguishes a decision-point task from an execution task. | "Dominic Review Required" / "Attorney Review Required" items, tool-migration choices (ClickUp vs Notion), entity-structure picks | Overlaps with almost anything (Governance, Legal, Vendor). Exists specifically because DECISIONS.md calls out Operating Agreement review items becoming tracked tasks — this label is how they get found. |
| 5 | **Legal / Compliance** | Requires legal review, filing, regulatory or licensing compliance. | Operating Agreement, permits, entity formation, health-dept/licensing tasks | Distinct from Governance/Structure (org design) even though both can appear on the same task (e.g., the Operating Agreement is both). |
| 6 | **Capital Spend / Budget** | Involves money commitment, budget tracking, or capital-stack decisions — the financial dimension of a task, regardless of department. | Budget Review series, FF&E/OS&E line items, reserves, lease financial terms | Overlaps with Build (most capital spend is one-time build) and Vendor/Procurement. Does not replace a dedicated Budget/amount custom field if one is added later — this is a coarse "money is involved" flag. |
| 7 | **Investor / Fundraising-Facing** | Anything customer-facing to investors/lenders — outreach, materials, relationship tracking, pitch content. | The `investor`-tagged cluster, named-investor outreach tasks, pitch deck, white paper, investor website | This is the field-driven signal the Investors & Fundraising carved-out Punch List view filters on (per DECISIONS.md: carve-outs "driven by a field value... not by task names"). Recommend also retiring the informal `investor` Tag once this label is populated, to avoid two parallel signals (flagged as a conflict below — see §5). |
| 8 | **Real Estate / Buildout-Facing** | Anything tied to the physical space — lease, construction, permits-for-space, site logistics. | 207 St. Elmo Rd lease, rent terms, construction milestones | This is the field-driven signal for the Real Estate/Buildout carved-out view. Mutually exclusive in practice with Investor/Fundraising-Facing, though both could theoretically co-occur (e.g., a lease negotiation that's also a capital-raise condition) — allowed, not typical. |
| 9 | **Vendor / Procurement** | Selecting, contracting, or managing an external vendor or SaaS tool. | Tool migrations (Box, Airtable, ClickUp billing), FF&E vendor selection, uniform vendor | Overlaps with Capital Spend and Build. Distinct from Legal/Compliance (a vendor contract might trigger legal review — two labels, not one). |
| 10 | **Research / Exploration** | Open-ended investigation where the answer isn't known yet — the "high uncertainty/novel" bucket borrowed loosely from Cynefin's complex/complicated framing, described in plain language rather than Cynefin jargon. | Entity-structure research, this very Phase 3 research track, competitive/market research | Mutually exclusive with Recurring/Operating (research is inherently bounded/one-time within its own investigation, even if the topic recurs as a new question). Can pair with Founder Decision (research feeding a decision). |
| 11 | **Admin / Housekeeping** | Low-stakes account/access/logistics cleanup — not a decision, not a deliverable, just needs doing. | "transfer ownership from brandon" ×3, Gmail/Airtable/Access Removal single-word tasks, billing cleanups | Exists specifically to give the audit's flagged "leftover admin tasks" (DECISIONS.md: "keep them; give them proper names and owners") a home so they don't get miscategorized as Build or Governance. |
| 12 | **Brand / Design / Guest Experience** | Work that shapes what the guest sees/feels — brand system, menu, uniforms, guest-facing design. | 1A–12A brand & design register, uniform lookbook, brand guidelines | Distinct from Build (Build is about internal systems/infrastructure existing; this is about outward-facing identity, even though both can be one-time setup work — a task can carry both Build and Brand/Design). |

### Values considered and deliberately excluded
- **Cynefin's five domain names** — too academic for two-person daily use; the underlying "how well-understood is this" idea is folded into *Research/Exploration* vs. everything else instead of a 5-way split.
- **GTD-style context labels (@calls/@errands)** — wrong altitude; those describe *where* work happens, not its nature, and ClickUp already has task type + assignee for that.
- **A raw "Urgent"/"Important" pair** — duplicates native Priority and the Inbox→Later→Soon→Next status queue; would violate the "don't duplicate an existing axis" instruction.
- **A literal "R&D" label** — folded into *Research/Exploration*, which is broader and matches Sŏn's actual content (there's no product-engineering R&D here, but there is a lot of "we don't know yet" investigation).

## 4. Proposed custom task-type set (Capture lists + Punch List)

DECISIONS.md already commits to task types (not a field) for Capture-list item kind, naming Deliverable, Structure, Workflow, Idea, plus Meeting/Document already live in the Punch List (per the audit). Full recommended set, unified across Capture lists and the Punch List so both use the same types workspace-wide (ClickUp task types are a workspace-level setting shared across spaces):

| Task type | Use | Already in use? |
|---|---|---|
| **Task** (default) | Fallback for anything that doesn't need a specific type — most current Punch List rows. | Yes (default blank type) |
| **Meeting** | A meeting occurrence or its series parent. | Yes (confirmed in audit) |
| **Document** | A doc-producing task (agenda, template, write-up). | Yes (confirmed in audit) |
| **Deliverable** | A concrete artifact to be produced (a plan, a packet, a design file) — the Capture-list item kind. | Decided, not yet built |
| **Structure** | An org/process structure being defined — pairs with the Governance/Structure Classification value but at the item-kind level (e.g., "define the reporting structure" as an item, distinct from the Classification label on any task about it). | Decided, not yet built |
| **Workflow** | A repeatable process/procedure being designed. | Decided, not yet built |
| **Idea** | An unvetted idea captured for later triage — the standard "Captured" status entry point. | Decided, not yet built |
| **Decision** *(new recommendation)* | A discrete founder decision point with options, not a deliverable or a meeting — gives "Dominic/Attorney Review Required" items and open questions a proper shape instead of overloading the Founder Decision Classification label to also carry the task's *kind*. | Not yet decided — recommend adding |
| **Milestone** *(new recommendation, ClickUp native default type)* | A dated checkpoint with no deliverable of its own (funding close, lease signed, opening date) — useful given the Punch List's "until past funding + lease" gating language in STATE.md/DECISIONS.md; gives that gate a literal task/milestone to point at. | ClickUp ships this as a default type; recommend enabling it, not custom-building |

This keeps task type answering "what shape of thing is this" while Classification answers "what's its nature" — e.g., a task can be type=Decision + Classification=[Founder Decision, Legal/Compliance], or type=Meeting + Classification=[Recurring/Operating].

## 5. Conflicts to flag

1. **`investor` Tag vs. Investor/Fundraising-Facing Classification value** — the audit found one existing Tag (`investor`) applied inconsistently to ~12 tasks (audit: founding-son.md §Tags). Once Classification's Investor/Fundraising-Facing value is populated, having both a Tag and a Classification value carrying near-identical meaning is redundant and will drift out of sync. Recommend: migrate the `investor` tag's intent into the Classification value and stop using the Tag for this purpose (Brandon approval needed — Tags weren't decided in DECISIONS.md).
2. **Governance/Structure must be explicitly excluded from carved-out views** — DECISIONS.md is explicit that Scaling People never appears in Investors or Real Estate carved-out views, and that carve-outs are field-driven. Because Classification is multi-select, a Scaling People task could technically also get tagged Legal/Compliance or Founder Decision without also getting Governance/Structure — the view filter logic needs to be "include if Investor/Fundraising-Facing OR Real Estate/Buildout-Facing," not "exclude if Governance/Structure," or a Scaling People task with a stray second label could leak into a carved-out view. Flagging as a build-time filter-logic risk, not a naming problem.
3. **Task type "Structure" vs. Classification value "Governance/Structure"** — same word, different altitude (item kind vs. effort nature). Recommend renaming the Classification value to plain **"Governance"** (dropping "/Structure") at build time to avoid the two fields looking like duplicates in the UI, even though their meanings differ. This is a naming-collision risk only, not a scope duplication — flagging for the Phase 3 blueprint to resolve.
4. **Project field removal vs. Budget/Financials meaning** — DECISIONS.md says Project's intent "becomes the Classification field." The old Project dropdown had a `Financials` value; that intent is now split across *Capital Spend/Budget* and *Investor/Fundraising-Facing* rather than one value — confirm this split is acceptable before removing Project.
5. **AI auto-classification risk** — turning on ClickUp AI's 2026 auto-classify-by-content feature for this field would spend rollover credits and could mis-sort ambiguous multi-label cases (e.g., an Operating Agreement task is legitimately both Legal/Compliance and Governance) — recommend manual/deliberate population only, consistent with the AI-credits constraint in STATE.md.

## 6. Coverage check against the audit's 491-task groupings

Every group in the audit's "natural groupings" table maps to at least one Classification value: Scaling People backlog → Governance; S1–S17 book chapters → Governance + Research; Investors & fundraising → Investor/Fundraising-Facing; Legal/entity → Legal/Compliance (+ Founder Decision on review items); Budget/capital stack → Capital Spend/Budget; Real estate/lease → Real Estate/Buildout-Facing; Brand & design → Brand/Design/Guest Experience; Staffing/uniforms → Recurring/Operating (once live) or Build (initial setup) + Brand/Design (uniforms); Website → Build or Investor/Fundraising-Facing depending on content; Recurring meetings → Recurring/Operating; Tool/platform migration & admin → Vendor/Procurement or Admin/Housekeeping; Personal/misc → Admin/Housekeeping. No group is left without a value, and no value exists solely to cover one group.
