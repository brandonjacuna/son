## Findings

| Severity | Location | Issue | Fix | Status |
|---|---|---|---|---|
| **HIGH** | `05-build-plan.md` 0.1; `04-knowledge-docs.md` §6 Step 1 | **Confirmed empirically:** `clickup_filter_tasks` returns only a compact per-task summary (id, name, status, priority, assignees, tags, dates) — it has **no** `include`/expand parameter and does **not** return custom field values or descriptions. Both the baseline export ("custom fields expanded") and the SaaS Map "full field-by-field export" (241+46 rows, the plan's lossless-export baseline that DECISIONS.md's export-verify-approve gate depends on) assumed `filter_tasks` alone could pull every field. As written, the exported CSV would be missing every custom field and full description, and the Step-3 verification checklist would pass its row-count check while silently missing the actual field data — defeating the "lossless" requirement. | Reworded both steps to a two-pass technique: `filter_tasks` (paginated, `include_closed: true`) to enumerate task IDs, then `clickup_get_task(task_id, include: ["custom_fields","description"])` **per task** for the real values. Time estimate for 0.1 revised from 20 min to 2–3 h (~900 individual `get_task` calls across the protected sets + SaaS lists). | **Fixed** |
| **HIGH** | `02-workspace-structure.md` §3 (Owner Notes); `05-build-plan.md` 3.4 | The Owner Notes migration bulk-writes a new field across the Founding Punch List — the same list that holds the ~330 protected Scaling People tasks — but, unlike the parallel Classification pass (3.8, which explicitly says "never Scaling People"), it had **no exclusion guard**. - **Scaling People / Carryover Register never touched:** compliant except the one gap fixed above (Owner Notes migration guard). Stage 5.1's protected-set diff is the backstop either way.
